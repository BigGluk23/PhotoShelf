# Working catalog in 0.10.0

`SqliteDesktopCatalogStore` is the authoritative store used by the Windows desktop. The retained table name `desktop_media_items` is a compatibility name; this is now a stable-identity catalog with an asset ID, normalized Windows path/folder keys, persisted file/capture dates, metadata state, quarantine state, and indexed paged queries. The older rich domain schema remains available for future metadata integrations; it is not populated as a second copy by the Desktop. Unifying the active read/write path avoids an untested rewrite of that unused schema.

`SavedMediaItem` is the bounded catalog DTO. The Desktop requests a group summary and pages; it must not call `LoadAsync(includeItems: true)` to populate a global UI collection. That overload remains only for legacy import/tool/test compatibility. Sequential background enumeration uses a keyset cursor; random viewport access uses indexed offsets, normally within a month. Filters, dates, folders, favorites, recent selection, and group counts are SQL operations. Cursor identity includes the view and uses the persisted SQL sort key.

Scans upsert in 256-row transactions and preserve favorites. A partial scan never implies deletion of missing or offline files. Favorites and metadata are explicit targeted updates; a stale metadata result must match the current path/size/mtime. All working stores share one writer gate. Every connection uses `synchronous=FULL`; the database uses WAL. Move callbacks return only after a transaction commits the stable identity, legacy metadata/hash paths, quarantine state, and idempotency receipt. Destination collisions stop reconciliation instead of replacing another asset. Reverse movement restores quarantined identity and user data.

The serialized upsert connection uses a suggested 32 MiB SQLite page-cache budget to reduce index-page churn during ingestion. Other connection checkouts explicitly restore SQLite's ordinary 2000 KiB budget, including reused pooled writer connections. This changes neither the 256-row commit boundary nor WAL/FULL durability, cache-spill policy, schema or media bytes. The budget concerns cached database pages, not a hard limit on total process memory. See [SQLite cache_size](https://www.sqlite.org/pragma.html#pragma_cache_size).

The size-count table is maintained by SQLite triggers in the same transaction as the asset update. Duplicate candidate enumeration reads its partial index rather than repeatedly grouping the entire catalog. The hash cache uses size and modification time as its reuse fingerprint; file-operation safety must independently verify bytes before cleanup.

Before migrating v0.9.7, the application checks the source, creates a SQLite backup (including committed WAL pages), verifies it with `integrity_check`, flushes the completed file, and publishes its `.sqlite` name with a durable no-overwrite rename (Windows WRITE_THROUGH; Unix directory fsync). Until verification succeeds, the candidate has a `.pending` suffix. Failed/partial backups are retained rather than guessed safe to remove. Ambiguous normalized paths abort the migration transaction and preserve the old schema and rows. Manual backups use the same procedure.

Do not restore an old catalog while the application runs. Catalog snapshots are not copies of photo/video originals. Restoring an older catalog can also restore older move receipts; coordinate offline recovery with the file-operation journal and reconcile filesystem paths before further operations. The application therefore exposes verified backup creation, while automated restore of arbitrary old snapshots is deliberately not a file-operation recovery mechanism.

Tests cover migration rollback/backup integrity, Unicode path and date query parity, keyset/offset equivalence, filters, stale metadata suppression, quarantine restoration, duplicate counters, and bounded page access at 10,000 / 100,000 / 1,000,000 records. SQL timings are diagnostic measurements on the execution host, not WPF responsiveness measurements on Windows.

## Filesystem observations in 0.10.6 (schema 5)

Schema 5 adds `availability`, its UTC check/error, optional opaque OS `file_identity`, and monotonic `observation_version` to each working media row. Existing rows become **NeedsVerification**, not missing. The migration creates and verifies a durable SQLite backup before altering the old schema. `watched_folders` is a separate additive JSON setting: tree navigation and a drive being visible never imply permission to import that whole drive.

Availability is Available, Missing, RootOffline, AccessDenied, or NeedsVerification. Unavailable observations update only status/revision: the asset, file fingerprint, capture date, favorite and known OS identity remain intact. Rows are not deleted or quarantined by observation. Root/subtree updates use short 256-row transactions and preserve newer individual observations. Availability must be established for each file, never inferred from a root merely existing. Default views keep unavailable records visible; metadata/duplicate work skips known missing/offline/denied records and NeedsVerification records with an explicit probe error (including reparse/physical-path mismatch). Only error-free legacy NeedsVerification records remain eligible for a first read.

`ApplyObservationAsync` and bounded `ApplyObservationsAsync` compare the complete expected asset/path/size/mtime/observation revision inside the write transaction. A null expected snapshot is **insert-only**, so an unknown-file race cannot overwrite an already cataloged asset. Confirmed fingerprint/identity changes invalidate derived date/hash caches; a change event can force revalidation even when size/mtime match. Event suspicion alone retains the previous known date until an authoritative metadata result. Metadata and duplicate-hash workers must use the observation-version guard (`UpdateMetadataResultAsync(... expectedObservationVersion: ...)`, `DuplicateHashStore.SaveObservedAsync`) so a delayed result cannot resurrect an invalidated cache. Legacy unguarded adapters remain for old imports/tests, not live filesystem reconciliation.

External rename reconciliation is separate from journaled `MoveItemAsync`. The caller must freshly establish that the old path is absent and destination still matches its probe. The transaction additionally requires one unique nonempty OS identity, an exact fingerprint, an unchanged source revision, and no destination catalog collision. It preserves the same asset, favorite, capture date and valid derived hashes; ambiguity refuses the merge. It never creates or consumes a file-operation receipt. The journaled move callback clears the old OS identity and marks the destination NeedsVerification because a cross-volume transfer creates a different filesystem object. Neither observations nor stale scan results can resurrect a quarantined row.

Path-subtree and known-folder readers are bounded keyset pages. Stable OS identities have a partial SQLite index; unavailable observations retain identities to permit conservative reconciliation after reconnect. An OS identity is not proof of unchanged content, and identity matching does not replace fingerprint/read checks or file-operation safety verification.

## Storage admission and update isolation in 0.10.13

Normal Desktop startup must explicitly discover and activate storage before a default store can resolve its directory. `CatalogLocation` pins the durable generation identified by `storage-selection-v1.json`; missing/inaccessible/broken selected storage never falls back to an empty catalog. First transition copies the selected historical Local/Roaming source via SQLite Backup API and exact JSON/journal copies, validates the target, then durably publishes generation manifest and selector. Keep source files and incomplete candidates. Two populated sources require user selection, not merge. Acquiring the new working copy must not rewrite absolute checksummed undo links: `JournalPathRelocation` maps only the chosen old/current operations directories.

`InitializeAsync` rejects unknown/future/mismatched schema before writes. The explicit startup `InitializeAndImportLegacyAsync` additionally checks persisted path/folder keys and imports legacy JSON with a separate completion marker. Items, missing preferences, reusable hashes and marker commit in one transaction. Existing paths/favorites are preserved. Full old settings or move/quarantine evidence make SQLite authoritative; partial rows or a random setting alone do not prove import completion. Invalid JSON fails closed; no file probing or JSON rewriting occurs during import. Known offline items remain catalogued. Ordinary initialization does not repeat the full semantic key scan.

The storage copy protects catalog format compatibility, not concurrent operations by old applications over shared media. Close old applications before upgrading and never move the same files through two versions. Catalog restoration and filesystem-operation recovery remain separate procedures.
