# Background observation contract

`LibraryChangeCoordinator` owns the watcher lifecycle and one background callback at a time. It never writes originals or SQLite. The Desktop callback reconciles bounded catalog batches and checks its cancellation token before publishing a view. Do not call the coordinator's lifecycle methods from its callback (the lifecycle waits for that callback).

`ConfigureAsync` copies paths, cancels and drains the previous callback, preserves watchers for unchanged roots and reconciles added roots. Changes to recursion, ignored directories or the `ShouldObservePath` delegate require reconciliation. Supply an immutable, in-memory predicate; reuse its delegate when its rules have not changed. Root configuration must contain actual library/browsing scopes, not every drive merely displayed in the tree.

Manual searches share this worker through `ReconcileAsync(paths, token)`. A request joins a pending or active full pass covering its paths; after that pass has completed, a new request schedules a new pass. A selected child of an existing recursive root uses a targeted directory reconciliation, without requesting a new pass over its whole drive. Paths must have a configured owner; unsupported scopes fail explicitly. Requests are bounded to 256 concurrent waiters, with at most `MaximumRoots` distinct paths per waiter.

When a search changes configuration, use `ConfigureAndReconcileAsync(configuration, paths, token)`. It registers the request under the coordinator lock before starting the configured worker and returns a `LibraryReconciliationRequest`: configuration has finished, while `Completion` awaits the real callback. Separately calling `ConfigureAsync` and then `ReconcileAsync` would race a fast initial pass and could start a second pass. The configuration task itself must not include the callback wait, so Stop and file-operation preparation can still await configuration and then drain the worker.

`Completion` succeeds only after all requested scopes finish a callback successfully in an active generation. Consumer failure and callback cancellation retain pending intent. Cancelling a caller only cancels its wait; it neither acknowledges queued work nor certifies that readers have stopped. Stop must also await `PauseAsync`. Reconfiguration transfers waiters to a covering owner or cancels them when their coverage is removed/narrowed; disposal faults remaining waiters instead of leaving them pending. `ResumeAsync(reconcileAllRoots: false)` resumes interrupted/queued work without adding a fresh full pass for every otherwise quiet root; the default remains the full reconciliation used by ordinary global resume.

`PauseAsync` cancels and waits for the actual callback and synchronous probe to finish. Native directory watchers remain open and only enqueue bounded notifications; no probes, media reads or catalog callbacks run while paused. On Windows, .NET opens directory handles with `FILE_LIST_DIRECTORY` and `FileShare.Read | FileShare.Write | FileShare.Delete`, then reads directory notifications; it does not open the individual media files. See [.NET 10 implementation](https://github.com/dotnet/runtime/blob/v10.0.0/src/libraries/System.IO.FileSystem.Watcher/src/System/IO/FileSystemWatcher.Win32.cs). Cancellation alone does not prove that a reader finished. Configuration changes retain an explicit pause and keep pending paths belonging to surviving scopes. `ResumeAsync` starts a fresh generation, replays pending paths and requests ordinary snapshot reconciliation for retained roots. A quiet pause/resume does not invalidate unchanged content caches. Cancelled path batches return to the same bounded queue; only overflow escalates to forced root content revalidation. `DisposeAsync` drains and closes everything. A blocking OS/network call can delay draining; never begin a file mutation merely because cancellation was requested.

Defaults and bounds:

- At most 4,096 configured roots; exceeding the limit fails explicitly. At most 32 root subscriptions, each with two native watchers (file notifications and directory names), using 24 KiB of native buffers per root. Further roots retain periodic reconciliation and expose `NeedsVerification / WatcherLimitPeriodicFallback`.
- At most 1,024 deduplicated pending file paths and 256 paths per callback. File-event overflow retains the affected root in a bounded FIFO reconciliation queue and requests content revalidation. One full root reconciliation is delivered per callback. A continuously dirty root cannot starve other roots.
- Directory notifications have a separate bounded queue of at most 1,024 targets, with at most 32 targets per callback. Each target retains its watched owner root and the changed directory path; queued descendants coalesce into their parent. A rename retains both old and new subtrees. Directory-queue overflow falls back to a full pass of the affected owner, without invalidating every file's content caches. A full owner pass covers its already queued targets; notifications arriving during the pass retain fresh intent. Cancellation, pause, reconfiguration and consumer failure retain or conservatively widen that intent instead of dropping it.
- First-event debounce is 250 ms; continuous writes cannot postpone a batch indefinitely. Root availability is probed every 30 seconds. After a successful full reconciliation the next periodic reconciliation is due 30 minutes after completion, even when the previous pass itself took longer than 30 minutes. Genuine events queued during the pass still run without waiting for this periodic interval. A long running callback delays subsequent probes; callbacks must scan incrementally and honor cancellation between I/O operations.
- Native error/overflow events and recovery after an unavailable root or failed/restarted watcher force root reconciliation and content invalidation, even if file length and mtime did not change. Errors and overflow arriving during a pause retain these force flags until processing resumes; keeping healthy watchers open avoids a gap during ordinary modal reviews. `RevalidateContentRoots` survives cancelled/failed callbacks. Ordinary startup/periodic reconciliation compares known snapshots rather than invalidating all hashes unconditionally. Content edits preserving size/mtime made while the program was closed cannot be identified by metadata comparisons alone.
- File rename notifications include both old and new paths. Directory name notifications reconcile only the changed subtrees under their original observation scope. Deleted/inaccessible subtrees are checked against the catalog without removing records or declaring the entire owner drive unavailable. An ordinary file creation does not request a complete root scan.
- `.photoshelf-*` path components and configured internal directories are ignored. They must never be removed as caches.

`FileSystemObservationProbe` performs synchronous, read-only metadata I/O on a worker. It distinguishes `Available`, `Missing`, `RootOffline`, `AccessDenied`, and `NeedsVerification`; failures do not fabricate replacement lengths, dates or identities. It checks ancestor reparse points, opens Windows metadata handles without write access and with `OPEN_REPARSE_POINT`, verifies the physical handle path, and combines 128-bit `FILE_ID_INFO`, volume serial and creation UTC ticks. Unsupported identity APIs and non-Windows systems provide no identity. Identity is a hint for conservative matching, not a content hash: the catalog must also verify that the old path is genuinely missing and reject ambiguous candidates.

`Activity` returns a detached, thread-safe `LibraryMonitorActivity` snapshot, including paused/disposed/processing state, active full roots or directory targets, bounded pending file/directory/root counts, and successful full-root/directory reconciliation counters. It remains readable after disposal. It does not enumerate files, query SQLite, or prove that the application's separate scan/metadata workers are idle. Optional `TimeProvider` injection permits long-interval scheduling tests without a 30-minute wall-clock wait; production uses the system clock.

Synthetic tests cover real watcher delivery, quiet pause/resume without broad content invalidation, paused event collection and bounded overflow, cancellation replay, reconfiguration, explicit pause during file operations, synchronous drain, retry/fallback, offline reconnect, fairness, and unchanged source bytes/mtime. A controlled clock tests a callback lasting beyond the periodic interval, while real event barriers check that the next pass waits and that new directory/error intent is retained. Targeted directory tests cover continuous nonmedia noise, discovery, rename identity and missing-record retention. Windows CI must additionally run native stable-ID and junction tests; portable passes do not prove those Windows contracts.
