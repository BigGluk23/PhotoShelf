# PhotoShelf v0.10.0: изменения и проверка

Дата: 27 сентября 2026. Исходная версия в переданной папке при начале работы: v0.9.7.
Среда проверки: macOS ARM64, .NET SDK 10.0.401 / runtime 10.0.12.

## Что мешало скорости и безопасности

1. Главный экран удерживал коллекцию всей библиотеки и заново строил строки при переключении даты/вида. Теперь фильтрация, порядок и группы вычисляются SQLite, а UI материализует ограниченное число страниц.
2. Фоновый запуск сам по себе не ограничивал конкуренцию декодеров и рост кэша. Добавлены ограниченная очередь, приоритеты, резерв для интерактивной работы, бюджеты и освобождение выгруженных превью.
3. Синхронные читатели могли продолжать держать файлы после отмены. Перед переносом ожидается фактическое завершение сканирования, индексирования, хэширования и затронутых декодеров; окна просмотра закрываются.
4. Файловая система и SQLite не образуют общую транзакцию. Теперь используется проверяемый журнал с повторяемыми шагами, устойчивыми идентификаторами объектов и квитанциями фиксации в БД.
5. Удаление по пути после проверки оставляло гонку подмены файла. В Windows завершение исходного файла привязано к тому же открытому и проверенному файловому handle.
6. Старые зависимости SQLite обновлены; проект переведён на .NET 10. Проверка зависимостей не обнаружила известных уязвимых пакетов на момент сборки.

Проверяются конфликты и отсутствие перезаписи, изменение исходника, повреждённые/оборванные журналы, ошибка фиксации каталога, повтор восстановления, отмена, группы companion-файлов, откат с занятым исходным именем, подмена staging, повреждение копии. Подпроцесс принудительно завершается после staging, проверки копии, публикации назначения, фиксации каталога, завершения источника и переименования на одном томе. После каждого сценария проверяются SHA-256 сохранившихся байтов, восстановление и повторный запуск восстановления.

Интеграционные тесты используют настоящий SQLite: сбой после FULL commit до записи подтверждения в журнал, частичная фиксация группы с повтором, карантин/откат с сохранением stable ID, избранного, дат и файлов. Все файловые сценарии используют искусственные временные файлы, не библиотеку пользователя.

## Обязательная проверка на Windows

1. На копии библиотеки запустить `scripts/verify-windows.ps1`. Скрипт требует Windows и считает пропущенные тесты незавершённой проверкой. `-Scale` добавляет три масштабных сценария.
2. Запуск с сохранённой папкой, режимом дат, избранным и раскрытым деревом: отсутствуют показ неверного вида и последующий сброс. Проверить повторный запуск, закрытие во время загрузки и второй экземпляр приложения.
3. На библиотеках 10k/100k/1M быстро менять папку, даты, сортировку, поиск, галки и масштаб; прокручивать далеко вниз, открывать точный выбранный кадр. Старые запросы не подменяют новый вид, placeholders заполняются, UI принимает ввод.
4. Измерить на явно записанном компьютере холодный/тёплый старт, первую страницу, клики во время индексации, пиковую память и прокрутку. Начальные цели: p95 реакции на ввод до 100 мс, первая полезная страница прогретого каталога до 500 мс. Сейчас эти UI-цели не подтверждены. CSV Dispatcher lateness служит диагностикой и не заменяет измерение ввода.
5. GIF, WebP, animated WebP, большие изображения, повреждённые файлы, видео/перемотка, переключение и закрытие viewer; многократная прокрутка не вызывает постоянного роста кэша.
6. Перенести группы JPEG/RAW/XMP/AAE в пределах NTFS, затем между дисками; проверить SHA-256, даты, избранное, конфликт имён и откат. Live Photo с неоднозначной связью должен быть отклонён. Проверить длинные пути, кириллицу, различия регистра, read-only, занятые файлы, нехватку места, отключение USB, FAT/exFAT timestamps.
7. Проверить native sharing/delete-handle и ADS/EFS тесты на NTFS, а также остановку процесса в контрольных точках. После перезапуска «Операции» восстанавливает состояние, повтор не дублирует действие; неизвестные/изменённые файлы сохраняются.
8. В дублях повторно проверить keeper, карантин, частично неуспешную операцию, повторный клик и закрытие окна/приложения. Пока есть незавершённый журнал, новая обработка заблокирована.
9. Мигрировать копию базы v0.9.7: проверить резервный `.sqlite`, integrity_check, даты, избранное и недоступный диск. Проверить ошибку создания резервной копии: миграция не должна продолжиться без неё.

## Восстановление и ограничения

- Начните с окна «Операции»: прочитайте план и используйте «Продолжить» или «Откатить». Откат создаёт собственный журнал и не перезаписывает появившийся файл на исходном месте.
- После ошибки файл может уже быть в целевой папке, пока каталог ожидает согласования. Не создавайте повторный перенос и не удаляйте `.photoshelf-*` файлы вручную. Приложение предпочитает сохранить лишнюю копию.
- Резервная копия SQLite не включает оригиналы. Не подменяйте базу при работающем приложении. Старая база содержит старые квитанции: её восстановление требует отдельной сверки с журналами и реальными путями.
- Автоматический разбор старых журналов v0.9.7 заблокирован: их данных недостаточно для достоверного восстановления. Требуется ручная проверка сохранённых файлов.
- Windows обеспечивает очистку через проверенный handle. На macOS/Linux тестовая реализация намеренно оставляет исходный staging под журналируемым резервным именем: безопасный эквивалент удаления по открытому handle отсутствует.
- Отключение питания, аппаратная порча и потеря диска не проверены. Flush/write-through — запросы ОС, а не защита от неисправного накопителя. Независимая резервная копия оригиналов обязательна для защиты от потери единственного носителя.
- Полное декодирование HEIC/HEIF/RAW, Live Photo resolver по content ID и отказ от системных видеодекодеров остаются последующими этапами.
