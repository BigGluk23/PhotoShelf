# PhotoShelf Ultra v1.11.1: кандидат в выпуск

Техническая версия `1.11.1-ultra`, будущий тег `v1.11.1-ultra`.
Подготовка начата от `main` на `8c45571122d6d61ef731322754fe69c8573a05d9` после
принятия PR #13. Наличие этой страницы или сборки CI не означает публикацию релиза.

## Состав

- Исправлен потерянный повторный запрос визуальной индексации. Новые/изменённые фото
  за уже пройденным курсором автоматически обрабатываются следующим проходом.
  Запросы объединяются, кэш используется повторно, пауза/перенос/recovery/закрытие
  заново проверяются перед стартом. Отмена ждёт фактического освобождения читателя.
- В текущем `main` уже приняты отдельные режимы точных дублей и похожих фото,
  постраничный разбор, массовые правила выбора сохраняемой копии, предварительный
  план карантина и сравнение 2–4 файлов (PR #9–#11).
- Новая версия строго больше 1.11.0: после публикации подписанного стабильного
  релиза пользователь установленной 1.11 сможет получить предложение обновления.
  Скачивание и установка по-прежнему требуют отдельных явных действий пользователя.

Релизный PR меняет номер/видимые подписи, project references в lock-файлах и
документацию. Сторонние зависимости не обновляются. Схема каталога остаётся **5**;
оригиналы, алгоритмы переноса/карантина и встроенный публичный ключ этим PR не меняются.
Полная дорожная карта [v1.12](https://github.com/BigGluk23/PhotoShelf/issues/6)
не объявляется выполненной: задачи #3–#5 требуют отдельной приёмки.

## Проверки и ограничения

Функциональное исправление проверено в [PR #13](https://github.com/BigGluk23/PhotoShelf/pull/13):
778 Windows-тестов, включая девять сценариев повторного прохода и освобождения файлов.
Этот результат относится к ревизии PR #13, а не автоматически к новой версии.
Результаты кандидата должны быть приложены к его PR с точными head/base и ссылкой на CI.
После merge для выпуска нужен отдельный завершённый CI **итогового main SHA**.

Обязательный Windows gate проверяет сборку, TRX без failed/skipped, извлечённый пакет,
старт/просмотр/поиск/сортировку и оба сценария обновления: процессы installer и реальные
WPF controls с одноразовым тестовым ключом. Фикстура 1.11.0 → 1.11.1 сохраняется;
её версии намеренно не заменяются массовой подстановкой номера релиза.

Performance gate сравнивает 100 тысяч синтетических записей на одном Windows-хосте.
Это тёплые SQL/WPF-проекции, не замер декодирования, холодного старта или реальной
медиатеки. Миллион записей и отдельная ручная Windows-проверка не подразумеваются
обычным CI. Тесты не моделируют отключение питания и физический отказ диска.

Поддержка RAW/ProRAW, полных Live Photo/AAE/HDR и независимого видеодекодера остаётся
за рамками этого выпуска. Похожие кадры не являются доказанными дублями; их режим
не предлагает автоматический карантин. Перед публичным выпуском нужен ручной smoke
на выделенной синтетической библиотеке либо специально предоставленной тестовой копии.

## Финализация черновика требует отдельного решения

Текущий workflow не поддерживает второй dispatch `publish=true` поверх уже созданного
draft: существующий release/tag блокирует запуск, а rerun запрещён. Не удалять черновик,
не менять тег и не перезаписывать assets ради обхода этой проверки.

Штатный одноэтапный путь — один dispatch `publish=true` с предварительным owner approval;
после проверки байтов workflow публикует созданный им draft в том же job. Если выбран
двухэтапный путь `publish=false`, дальнейшая ручная финализация требует **отдельного
явного решения BigGluk23 для конкретного release ID/SHA/хэшей**. Это не второй защищённый
workflow и не автоматически перенесённое environment approval.

Перед такой финализацией владелец заново сверяет успешный release run и его approval,
main CI и отчёты, точный набор assets, их размеры/хэши, подпись manifest встроенным
публичным ключом и совпадение manifest с повторной unsigned validation кандидата.
Release должен оставаться draft, не prerelease, с ожидаемыми tag и полным target SHA;
существующий tag разрешается до того же коммита. Отсутствующий tag требует отдельного
create-only решения на этот SHA; неправильный существующий tag не перемещать.

Владелец исключает параллельное редактирование, проверяет отсутствие более нового
стабильного выпуска и публикует тот же release ID без изменения assets/подписи.
После публикации повторно читаются public release/latest и tag, скачиваются публичные
assets и сверяются с одобренными байтами. При расхождении публикация не считается
проверенной; исходные отчёты и файлы сохраняются для разбора.
