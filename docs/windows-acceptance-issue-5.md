# Windows acceptance: Issue #5 после PR #20

Добавление проверок к существующему harness не меняет поведение PhotoShelf, версию,
схему каталога, файловые операции или ключ обновлений. Issue #5 целиком не закрывается:
проверки будущего сценария организации файлов из Issue #4 остаются отдельно.

## Обязательные сценарии

`tools/harness.ps1` запускает `tools/test-wpf-acceptance.ps1`. Ошибка, пропуск,
неполный отчёт или несовпадение commit SHA останавливают Windows-проверку.
Стенд запускает три последовательных процесса настоящего WPF приложения:

1. Первичная визуальная индексация. В каталоге 100 000 отсутствующих синтетических
   записей и 200 реально созданных медиафайлов: 196 PNG, JPG, WebP, HEIC и MP4.
   AAE/XMP дают ещё два файла для проверки сохранности. Во время индексации выполняются
   24 перехода между началом и концом большой сетки; минимум восемь должны пересекаться
   с работающим fingerprint-проходом. Проверяется декодированная миниатюра медиа,
   ограничение страниц/строк кэша и очереди, пауза и продолжение без повторного декодирования.
2. Полное завершение EXE и новый процесс с тем же owned-каталогом. Сохранённая пауза
   восстанавливается до запуска фоновой работы. После продолжения неизменённые файлы
   не декодируются повторно; все поля fingerprint-кэша должны остаться идентичными.
3. Между процессами стенд намеренно меняет один собственный PNG и передаёт наблюдение
   через существующий production API. Следующий процесс должен декодировать только
   этот файл; AssetId и избранное сохраняются, меняется ровно одна запись кэша.

В первом процессе открываются настоящие `DuplicateSearchDialog` и
`DuplicateReviewWindow` для всей библиотеки и выбранной папки. Проверяются соответственно
34/18 групп, страницы групп и участников группы из 130 файлов, массовая отметка
162/146 лишних экземпляров, сохранение отметок за пределами страницы, защита keeper
и снятие всех отметок. Кнопки переноса/карантина не нажимаются.

## Сохранность и изоляция

Стенд принимает только новую папку `PhotoShelf-acceptance-<nonce>` непосредственно в
системном TEMP. Compile-time путь и marker должны совпасть. Путь пользовательского
каталога не принимается; reparse points в fixtures запрещены.

`prepare_windows_acceptance.py` копирует отслеживаемые исходники в эту папку. Только
в копии добавляются entrypoint, observer длительности SQLite commit, встроенный MP4
и тестовый драйвер. Shipping-проект не компилирует драйвер из `tools/`; его исходники
и ресурсы не изменяются. Отдельный test-copy EXE не включается в релизный пакет.
Отражение для выбора owned-каталога действует только внутри этой compile-time копии,
до создания `App`. Завершение по watchdog ограничено процессами из собственного output.

После каждого read-only процесса родитель сверяет SHA-256, размер и UTC mtime всех
202 оригиналов/companions, AssetId/избранное, отсутствие карантина и SQLite quick_check.
После намеренной мутации baseline оригиналов обновляется перед последним read-only
процессом. Каталог, fixtures и исходники стенд не удаляет. В CI-артефакты копируются
только пять явно разрешённых JSON-отчётов, без базы, медиа, EXE или пользовательских путей.

## Измерения и границы

Отчёт привязан к точному SHA и PID каждого реально запущенного процесса. Отдельно
собираются p95/max native fingerprint decode, SQLite batch commit и перехода к
загруженной странице. UI budget: Dispatcher gap и p95 страницы менее 5 секунд;
после четырёх прогревочных переходов рост private memory не более 256 МиБ;
кэш максимум 12 страниц / менее 2048 строк, pending queue максимум 256.
Это широкие регрессионные границы CI, а не обещание пользовательской задержки.
Существующее сравнение baseline/current на одном runner остаётся отдельной проверкой.

Чтобы гарантировать пересечение сетки с индексацией, только первый тестовый процесс
добавляет 90 мс перед fingerprint reader; эта задержка не входит в измерение decode.
100k отсутствующих записей создаются непосредственно в owned SQLite как fixture,
поэтому этот сценарий не измеряет импорт 100k физических фотографий.

Встроенный MP4 создан из красного кадра 32×32 длительностью 0,5 с:
`ffmpeg -f lavfi -i color=c=red:s=32x32:d=0.5:r=10 -an -c:v libx264 -pix_fmt yuv420p -movflags +faststart synthetic.mp4`.
Проверяются admission и сохранность байтов видео, без утверждения о playback.
HEIC использует существующий bundled decoder и синтетический fixture проекта.

Test entrypoint обходит admission установщика обновлений; `App.OnStartup` и реальное
окно проходят обычный путь. Обновления отдельно покрыты existing lifecycle harness.
Детекция filesystem notifications, физический сон/отключение диска/питания,
перенос/откат и quarantine execution этим сценарием не покрываются.
Миллион записей остаётся дополнительным Scale-прогоном. Ручной Windows smoke на
пользовательском оборудовании и отложенная организация файлов по Issue #4 ещё нужны.

## Запуск и диагностика

После чистого commit и сборки native HEIF codec можно запустить отдельно:

```powershell
./tools/test-wpf-acceptance.ps1 -ReportDirectory ./artifacts/acceptance
```

Обычный Windows harness собирает codec сам и запускает этот сценарий автоматически.
`windows_acceptance_checks.py` отклоняет пропуски, повторные PID, неверные счётчики,
перечитывание кэша, отсутствие scope/измерений и превышение budget.
Его негативные тесты не заменяют фактический Windows-прогон.
