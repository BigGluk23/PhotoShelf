# PhotoShelf Ultra v1.11: защита выпуска до публикации

Версия приложения остаётся `1.11.0-ultra` / **PhotoShelf Ultra v1.11**. Изменения готовят безопасный выпуск, но не являются разрешением загрузить ключ или опубликовать релиз.

## Выпуск и доступ

- Проверка кандидата выполняется отдельным read-only job без environment и без передачи байтов ключа.
- Наличие ключа в repository/organization scope запрещает выпуск. Подпись использует secret только из `release`.
- До запроса одобрения проверяются живые правила environment: обязательный BigGluk23, запрет self-review и только main. Отсутствующее окружение не считается безопасным.
- Второй job получает доступ через `environment: release`; проверяет фактическое одобрение владельцем конкретного запуска, неизменность environment ID, exact SHA и hash ранее показанного кандидата. Повтор запуска с прежним одобрением запрещён: требуется новый dispatch.
- Подписывается точный ZIP из успешного Windows CI, без пересборки. Черновик, загрузка и повторное скачивание с проверкой всех байтов предшествуют возможной публикации.
- Запрет admin bypass при отсутствии документированного REST-поля подтверждается владельцем в UI. CODEOWNERS и YAML сами по себе не включают GitHub branch protection.

Точные серверные настройки и подтверждённые ограничения прав: [release-protection-setup.md](release-protection-setup.md). Релизные workflow не запускались; ключ не отправлялся в GitHub.

## Проверки обновления

Windows harness дополнен двумя обязательными отчётами на точном исходном commit:

| Отчёт | Что действительно проверяется | Граница проверки |
|---|---|---|
| `updater-e2e.json` | Два реально скомпилированных процесса разных версий; production installer/process host; ожидание выхода родителя и освобождения файлов; повтор запроса/понижение версии; завершение helper до и после активации; сохранность synthetic originals/SQLite/journal | Вместо WPF-приложений используются явно помеченные console fixtures. Оба процесса собраны из текущего исходного кода |
| `updater-desktop-e2e.json` | Настоящие normal entrypoints WPF и helper; UI Automation нажимает установку; переход 1.11.0→1.11.1, startup receipt, настройки/поиск, оригиналы/каталог/журналы, старый ярлык | Одноразовый публичный test key подставляется только в отдельную копию исходников. Тестовые EXE не входят в релиз; реальный GitHub download и production-подпись не проверяются |

Никаких runtime override доверенного ключа или профиля в распространяемое приложение не добавляется. Тест реального WPF работает только на disposable Windows Actions runner при первоначальном отсутствии профиля PhotoShelf. Обнаруженный профиль — причина остановить тест, а не очистить его. Принудительно завершаются только процессы, принадлежащие синтетическому стенду.

Подпись блокируется без обоих отчётов, всех обязательных assertions/scenarios, совпадающих raw hashes и успешного Windows/performance CI. Кросс-компиляция macOS не подтверждает Windows runtime. Отключение питания и физическая поломка накопителя не моделируются.

## Повторный запуск во время установки

Прежний normal entrypoint проверял активную версию до получения mutex каталога и не учитывал блокировку установщика. Между выходом parent и публикацией указателя старый EXE мог начать открывать каталог; после публикации внешний запуск мог опередить successor установщика и лишить его квитанции готовности. Эти условия теперь отдельно проверяет детерминированный Windows regression-тест.

Normal startup удерживает допуск к запуску от проверки активной версии до захвата single-writer mutex приложения. Helper резервирует запуск ещё при живом parent; parent закрывается только после `helper-ready`, предварительного `parent-accepted`, подтверждения `helper-consumed` и финального `parent-committed`, привязанных к request и PID/starttime процессов. Ошибка или таймаут до финального подтверждения оставляют окно открытым; helper после фактического выхода parent требует именно `parent-committed`. Запоздалый предварительный ACK не превращает последующее обычное закрытие в установку. После финального подтверждения приложение завершает уже сохранённую сессию и не возобновляет работу с каталогом даже при исключении закрытия окна.

До проверки готовности новой версии установщик удерживает блокировку. Обычный повторный запуск показывает сообщение «PhotoShelf запускается или обновляется» и завершается после подтверждения сообщения, не открывая каталог. Запустить каталог в этот период может только successor с проверенными PID/starttime helper, удерживаемым claim, согласованными request и всеми подтверждениями передачи, подписанным manifest, SHA пакета, версией и точным путём активированного EXE. Его допуск также удерживается до single-writer mutex: таймаут или авария helper не позволяют следующей установке обойти ещё запускающийся successor. Факт существования оставшегося lock-файла не означает блокировку; владение определяется открытыми OS handles.

WPF harness вставляет контрольные остановки только в отдельную owned-копию исходников: `before-pointer-publish`, `pointer-published` и перед записью startup health. В каждой точке он запускает настоящий старый EXE без параметров, проверяет busy-диалог, код выхода 0, отсутствие входа в подготовку каталога и неизменность оригиналов/строк SQLite/журналов. Основной checkout и распространяемый EXE не получают переключателей тестовых остановок. Старый happy-path отчёт без трёх `repeatedLaunch*Blocked` assertions больше не подходит для выпуска. Точные результаты относятся к соответствующему Windows CI commit и отчёту; кросс-сборка не заменяет этот прогон.

## Ключ и восстановление

Локальная резервная копия рабочего RSA-ключа создана вне Git: PKCS#8, AES-256-CBC, PBKDF2-HMAC-SHA256 с 600000 итерациями, случайный пароль в выбранной по умолчанию macOS Keychain. Создание не перезаписывает существующие файлы, проверяет права доступа, фиксирует файлы и записи каталогов на диск. Исходный ключ сохранён.

Восстановление проверено в памяти: валидность private key, совпадение SHA-256 DER SubjectPublicKeyInfo с embedded public key и подпись/проверка случайного сообщения. Приватный ключ и пароль не печатаются, расшифрованная копия не сохраняется на диск. Шесть тестов покрывают восстановление, неизменность источника, запрет перезаписи, порчу шифротекста, неверный пароль/public key и небезопасные пути/права.

Это локальная копия, **не подтверждение восстановления после потери Mac**: для него нужны независимый носитель с зашифрованным файлом и пароль в отдельном хранилище владельца. `offDeviceRecoveryVerified=false` сохраняется явно. Действия при утрате/утечке и проект смены доверия: [update-signing-recovery.md](update-signing-recovery.md). Автоматический отзыв/ротация ключей не заявляются реализованными.

## Результат проверки

Точные результаты Windows запуска и SHA находятся в соответствующем GitHub Actions run и его `harness-summary.json`, TRX и двух lifecycle reports. До успешного завершения такого запуска новый набор проверок не считается пройденным. Более ранний зелёный CI v1.11 не содержит этих сценариев и не заменяет их.
