# v1.11.4: управляемая фоновая работа и длительные Windows-проверки

## Пользовательское поведение

В «Настройках» доступны «Тихий», «Сбалансированный» и «Максимальная скорость».
Сохраняется выбранный режим, прежние установки по умолчанию получают сбалансированный.
При вводе/прокрутке в окнах приложения в течение трёх секунд после события и при
питании от батареи фон делает более длинные паузы. Видимое превью сохраняет
зарезервированный исполнитель; явный просмотр выбранной папки не получает фоновую паузу.

Политика применяется к metadata, visual fingerprint и фоновой сверке/сканированию.
Она уступает время между завершёнными чтениями; это не фиксированный процент CPU,
не прерывание зависшего синхронного/native вызова и не уменьшение качества медиа.
Пауза/перенос/выход по-прежнему ждут настоящего завершения читателей.

«Операции» показывают режим, причину замедления, очередь/выполнение, число проверенных
записей, среднюю скорость прохода и возраст последнего результата. Чтение дольше минуты
отмечается как долгое: оно может ждать диск и не объявляется доказанным зависанием.
Ожидание очереди и снижение нагрузки отображаются отдельно. Сон не засчитывается как
доказательство зависшего читателя. Смена состояния питания не запускает переносов,
сброса каталога или принудительного завершения процессов.

Временные ошибки metadata повторяются через 5 минут, 30 минут, 6 часов, затем не чаще
раза в сутки. Счётчик представлен уже сохранённым интервалом attempt/retry и переживает
перезапуск. Повреждённые/неподдерживаемые файлы сохраняют terminal-статус до изменения
наблюдения или явной переиндексации. Известная дата съёмки при ошибке не стирается.

Экспорт поддержки получает структурированную историю до 120 снимков (около десяти
минут), CPU, память, очереди, задержку Dispatcher и счётчики задач. История сохраняет
максимальную задержку UI за интервал, включая ещё не завершившуюся остановку heartbeat.
Фотографии, пути,
имена файлов, поисковый текст и сырые исключения не попадают в этот экспорт.

## Проверки

- Application: режимы/приоритет ввода/батарея, ограничение пауз и истории, отличия
  чтения от ожидания, suspend/resume, отмена ожидания, fencing старой activity,
  устойчивый backoff без потери известной даты.
- SQLite: сохранение/загрузка режима через существующую таблицу настроек.
- Windows: synthetic offline/online probe при всех трёх режимах, сохранность ID,
  избранного, даты, SHA-256 и mtime. Это инъекция недоступности, не физический USB.
- Windows EXE: один процесс с production MainWindow, watcher, metadata и fingerprint
  worker. Маленькие PNG/JPEG/WebP/HEIC и повреждённый PNG, новые файловые события во
  время навигации, реальное декодирование видимых миниатюр и прокрутка, pause/drain,
  повторный проход без повторного fingerprinting неизменённых/повреждённых файлов.
  Отсчёт повторов начинается после завершения событий создания fixture: файловые
  уведомления первоначального поступления могут потребовать повторной проверки
  содержимого. Отчёт сохраняет начальные счётчики и запрещает их рост в тихих циклах.
- Циклы проверяют SHA-256/размер/mtime синтетических оригиналов и стабильные asset ID.
  Сбой UI ≥5 секунд и рост private memory более 256 MiB после первых трёх циклов
  прерывают gate. Это грубые пределы регрессии для fixture, не обещание скорости
  любой библиотеки. Фактические значения сохраняются в `ui-browse-smoke.json`.
  Отчёт также содержит среднюю нагрузку CPU за сеанс и максимальную среди интервалов
  между циклами, нормированные на число логических процессоров. Это CPU основного
  процесса; отдельный HEIC-процесс в эту величину не включён.

Обычный `tools/harness.ps1` требует 30 секунд soak и минимум три цикла. Длительный режим:

```powershell
./tools/harness.ps1 -BackgroundSoakSeconds 7200
# Дополнительно — синтетические каталоги 10k/100k/1M (не миллион файлов):
./tools/harness.ps1 -BackgroundSoakSeconds 7200 -Scale
```

GitHub Windows CI принимает `background_soak_seconds` (30..14400), `scale` и существующий
`performance_million`. Результаты привязываются к SHA/version. Failed/пропущенные
обязательные Windows-тесты или неполный soak блокируют пакет. Timeout оставляет fixture
для диагностики. Выпуски используют прежний подписанный workflow и существующий ключ.

## Границы

Soak не проверяет декодирование видео: существующая маленькая MP4 fixture проверяет
только учёт видео. Настоящие сон/пробуждение, смена батареи, отключение USB/SMB и отказы
накопителя требуют отдельного стенда; автоматические тесты моделируют сигналы/ошибки.
Для ручной проверки используются только синтетическая библиотека и её независимая копия:
дождаться idle, начать просмотр и сканирование, выполнить сон/пробуждение, отключить и
вернуть тестовый накопитель, проверить продолжение, сохранение записей и исходных хэшей.
Рабочий пользовательский каталог тестовым стендом не является.

Успешная кросс-сборка на macOS не подтверждает WPF/runtime. Длительный режим считается
прошедшим только по завершённому отчёту с фактической длительностью, не по запуску CI.
