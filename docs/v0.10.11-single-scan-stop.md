# PhotoShelf Ultra v0.10.11: один обход и завершённая остановка

## Проблема

При добавлении корня `RunScanAsync` регистрировал автообновление и одновременно запускал собственный `PhotoScanner`. Новый корень мониторинга тоже получал первоначальную сверку: возможны два полных обхода. «Остановить поиск» отменял только отдельный пользовательский обход, оставляя сверку работающей. Эта цепочка подтверждена исходным кодом; сама по себе она не устанавливает причину 12-часового инцидента на v0.10.8.

## Изменения

| Сценарий | До | Теперь |
|---|---|---|
| Новый корень библиотеки | Два независимых инициатора полного обхода | Один координатор; первоначальный запрос регистрируется до запуска worker |
| Повтор запроса во время обхода | Отдельный пользовательский скан | Ожидание уже выполняющегося подходящего обхода |
| Поиск во вложенной папке | Ручной скан отдельно от наблюдения | Адресный запрос поддерева; тихие соседние корни не добавляются при продолжении |
| Поиск на исключённом диске с включёнными подпапками | Scanner сам применяет правила дерева | Запрос координатору ограничен включёнными подпапками; исключённые соседи сохраняют своё состояние |
| Остановка | Отменяется только ручной поиск | Отмена поиска и просмотра, остановка сверки с ожиданием настоящих читателей |
| Обновление UI после остановки | Монитор мог продолжать обход | Guard сохраняет паузу до явного нового поиска/продолжения |
| Изменения файлов на паузе | Зависели от отдельного мониторинга | Watchers и ограниченные очереди сохраняются, включая overflow/recovery intent |
| Уже добавленные файлы | Сохранённые записи остаются | Тот же контракт; отмена не удаляет записи и не меняет оригиналы |

Таблица описывает устранённую дублирующую работу и поведение. Она не означает двукратное ускорение всей программы и не содержит неподтверждённых процентов CPU.

`ReconcileAsync` возвращает ожидание успешного callback. Отмена этого ожидания не выдаётся за освобождение файла: `PauseAsync` отдельно отменяет поколение и ждёт реальный callback вместе с публикацией уже зафиксированных данных. Настройка и ожидание обхода разделены, чтобы закрытие/перенос/Stop не блокировались циклическим ожиданием.

Кнопка показывает «Останавливаю поиск…» до завершения чтения; затем «Поиск остановлен · автообновление: пауза». Метаданные остаются отдельной задачей и видны в строке состояния/«Операциях»; для их остановки используется общая пауза. Просмотр выбранной папки после завершения Stop остаётся доступен и не возобновляет фоновую сверку. Остановка поиска действует в текущем сеансе, общая пауза по-прежнему сохраняется между запусками.

## Безопасность и проверка

Изменения не затрагивают протокол переноса/карантина, кодеки, схему SQLite и содержимое медиа. Прерванный обход не считается успешной сверкой. Ошибки доступа и отключённые диски не приводят к удалению строк. Ожидание файловых читателей перед переносом/закрытием сохраняется.

Проверки выполняются только на синтетических файлах. План регрессий: atomic initial request, присоединение к queued/active обходу, повтор после завершения, targeted child scope, отмена/пауза/смена конфигурации/ошибка callback, сохранение уведомлений и реальный Windows-сценарий Stop с удерживаемым читателем, SHA-256/mtime оригиналов и сохранёнными строками SQLite.

Локальные результаты на macOS: сборка решения — 0 ошибок/предупреждений; Application — 274 passed и 15 Windows-only skipped, включая 11 новых регрессий координатора и 3 проверки области поиска; SQLite — 139 passed; Domain — 4 passed; Python harness/report — 29 passed. Масштабные SQL-тесты в локальный прогон не входили.

В первом общем прогоне SQLite тест `ConcurrentCatalogRewriteCannotMixEndpointAndRangeSnapshots` упал с `ObjectDisposedException` внутри SQLite handle; отдельно тот же тест прошёл. Фикстуры вызывали process-wide `ClearAllPools` параллельно. Их выполнение теперь последовательное; намеренная конкуренция читателя/писателя внутри теста сохранена. Полный повтор дал 139 passed. Это изоляция тестового окружения, без изменения production DAL; точная причина первоначального единичного сбоя не установлена.

Четыре новые Windows-регрессии используют настоящее WPF-окно, отдельный TEMP-каталог, реальную SQLite и синтетические PNG. Управляемый callback удерживает настоящий read-only FileStream до освобождения барьера: это проверка ожидания читателя, а не обещание принудительного прерывания WIC. Дополнительно проверяются повторный Stop после поставленного в очередь поиска, изменение конфигурации после Stop, остановка до отложенного таймера галочки и поиск только включённого потомка исключённого корня. Независимое статическое ревью не выявило блокеров; runtime-результаты окончательной ревизии приведены ниже.

Первый [Windows-прогон 36576139467](https://github.com/BigGluk23/PhotoShelf/actions/runs/36576139467) на `2465e56` дал 520 passed / 1 failed / 0 skipped. Новый тест таймера галочки неверно создавал `RoutedEventArgs` без обязательного ClickEvent и был исправлен. Две другие новые Windows-регрессии прошли; скачанные TRX это подтверждают. Публикация EXE этим упавшим прогоном была заблокирована. Эти результаты не заменяют проверку окончательной ревизии.

Кросс-сборка на Mac не подтверждает WPF runtime. Остановка остаётся кооперативной: она не обещает принудительно прервать зависший системный вызов. Физические сбои носителя, отключение питания и личная библиотека пользователя не моделируются.
