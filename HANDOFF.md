# PhotoShelf: передача разработки

Текущая версия: **PhotoShelf Ultra v0.10.13** (`0.10.13-ultra`). Windows x64, C#/.NET 10/WPF.
Источник истины — https://github.com/BigGluk23/PhotoShelf, ветка `main`. Продолжение: `git pull --ff-only` и чтение `AGENTS.md`. Не переносите старый ZIP поверх checkout: архивы до v0.10.2 сохраняются отдельно как исторические поставки.

## Безопасное обновление v0.10.13

`CatalogLocation` больше не выбирает папку по Directory.Exists: нормальный старт обязан Discover → выбрать источник → PrepareAsync → initialize/import/load → CommitPrepared. SQL compatibility guard read-only; unknown/future schema не изменяется. Working generation изолирована от старых EXE, selection+manifest имеют identity, legacy source сохранён. Modern UndoJournalPath перенаправляется через `JournalPathRelocation`, checksummed bytes не переписываются. `LegacyJournalReviewService` только читает v0.9.7 и сверяет завершённые destinations по SHA-256; отдельная receipt не даёт права выполнять legacy recovery/undo. Не восстанавливать каталоги копированием старой DB поверх новой.

Windows harness создаёт manifest, распаковывает готовый ZIP и выполняет smoke на извлечённом EXE. HEIF preflight проверяет комплект без открытия фото, runtime допускает совместимые заменяемые LGPL-библиотеки. Подробности и точные результаты проверки: `docs/v0.10.13-safe-upgrade.md`.

## Координированный просмотр v0.10.12

`BrowseFolderAsync` больше не вызывает самостоятельный `PhotoScanner`. `LibraryBrowseTarget` фиксирует папку и глубину; координатор выполняет приоритетный запрос тем же worker и ждёт завершения настоящего callback. Запрос выбранной папки разрешён при `_searchStopped`, но не возобновляет фоновые события/dirty roots. Stop остаётся доступным для активного foreground; смена папки отменяет предыдущий запрос. `LibraryCatalogSynchronizer` для `BrowseTarget` использует отдельную точную область без library roots и без изменения inclusion rules. Конфигурация не ждёт traversal ticket; scope публикуется после drain прежнего callback. Результаты текущей проверки: [v0.10.12](docs/v0.10.12-coordinated-browse.md).

Windows job [36588441395](https://github.com/BigGluk23/PhotoShelf/actions/runs/36588441395/job/109474902332) проверил код `81b4fc8334b44149f795619444f749f9cadb931b`: 551 passed / 0 failed / 0 skipped. Скачанные TRX, EXE smoke, browse smoke и пакет проверены: целостность ZIP/SHA, сохранность синтетических оригиналов, фактическое завершение читателей/писателей. Переносы, recovery-протокол и схема базы в этом выпуске не менялись.

Общий workflow успешен, включая парное сравнение с v0.10.8 на 100 тыс. записей: 22 порога регрессии и 8 целевых UI-порогов пройдены, все media rows неизменны до/после каждого из четырёх процессов. Замер выполняется без декодирования и фоновых писателей и не измеряет отдельное снижение CPU от устранения двойного browse. Коммит с итоговым отчётом меняет только документацию.

## Поиск и остановка v0.10.11

Полные пользовательские поиски идут через `LibraryChangeCoordinator`, без параллельного `PhotoScanner` в `RunScanAsync`. `ConfigureAndReconcileAsync` атомарно регистрирует ticket до запуска первого обхода; конфигурация возвращается отдельно от `Completion`, иначе остановка может ждать сама себя. Запрос дочерней папки использует targeted directory queue. Отмена waiter не означает завершения читателей: Stop отдельно ждёт `PauseAsync`.

`MainWindow.Search.cs` ставит guard до отмены, ожидает callback/публикацию committed данных, отменяет отложенные checkbox scans и сохраняет их watched roots. Watchers и bounded recovery queues сохраняются на паузе. Обычный `QueueLibraryMonitoring` не снимает остановку; explicit search использует `ResumeAsync(false)`, без добавления всех тихих корней. Прерванные и новые события сохраняются. Глобальная пауза и её сохранение в settings остаются отдельным механизмом; остановка поиска действует в текущем сеансе. Метаданные управляются отдельно. Сборка/проверки этого выпуска: [v0.10.11](docs/v0.10.11-single-scan-stop.md).

`LibraryFolderScope.ReconciliationTargets` пересекает ручной запрос с действительными library roots: исключённый диск с явно включёнными потомками не становится запросом вне monitor scope и не расширяет наблюдение на соседей. Windows job [36578064246](https://github.com/BigGluk23/PhotoShelf/actions/runs/36578064246/job/109438725266) проверил код `5bb54bb1f95176b8dfcdd48a0562410d5c37ca5c`: 525 passed / 0 failed / 0 skipped, включая четыре новых WPF-регрессии и сохранность синтетических оригиналов. TRX, EXE smoke, SHA-256/целостность пакета скачаны и проверены; результаты и ограничения приведены в документе выпуска.

Весь workflow завершился успешно, включая сравнение с v0.10.8 на 100 тыс. записей: 22 порога регрессии пройдены, 8 целевых порогов UI выполнены, media rows неизменны во всех четырёх процессах. Это проверка запросов/проекций без декодирования и фонового индексирования; не приписывайте весь выигрыш этого сравнения исправлению обхода. Последующий коммит отчёта меняет только документацию, без изменения проверенного runtime-кода.

## Фоновые задачи v0.10.10

Периодический дедлайн сверки отсчитывается после успешного callback. DirectoryName notifications идут через bounded owner/subtree очередь; overflow и потеря наблюдения сохраняют отдельный recovery intent. `LibraryMonitorActivity` — только snapshot для UI.

`MetadataQueue.cs` использует partial pending-index и path keyset; UI query ordering не меняется. Результаты фиксируются пакетами с CAS по asset ID, fingerprint, observation version и предыдущему времени попытки. Commit короткий и не отменяется на середине; после него worker обязан опубликовать только accepted mask. `MainWindow.Metadata.cs` не отменяет активный проход на каждом завершении сканирования.

`BackgroundProcessingPaused` хранится в settings; guard включается до отмены и ожидания настоящих читателей. «Операции» показывают фон отдельно от истории переносов. `CaptureDateReader` имеет кооперативный stream budget, но не hard timeout зависшего нативного кода. Admission неоднозначных `.ts`/`.mts` выполняется только для новых строк, чтением не более 8 KiB; существующие строки сохраняются. См. [контракт и проверки](docs/v0.10.10-background-work.md).

Windows job [36564109481](https://github.com/BigGluk23/PhotoShelf/actions/runs/36564109481/job/109391752207) проверил код `4ff59b36ce1c03916caa1f945ebd006406e6887d`: 507 passed / 0 failed / 0 skipped, реальный EXE, WebP/HEIF, пауза/сохранение/продолжение/возврат к ожиданию, SHA/mtime синтетических оригиналов и завершение читателей. TRX, smoke и SHA-256 пакета скачаны и проверены. Этот короткий smoke не воспроизводит 12-часовой инцидент пользователя на v0.10.8 и не доказывает принудительное прерывание WIC. Последующие изменения документации не меняют проверенный runtime-код.

## Поиск и сортировка v0.10.9

В существующую транзакцию инициализации добавлены `ix_desktop_file_group_asc` и `ix_desktop_capture_group_asc`: `(is_quarantined,month,date ASC,path_key,flags,search_key)`. Они ограничивают ASC-страницу одним месяцем и покрывают обычную группировку поиска. Старые индексы, SQL-семантика и schema version 5 сохранены. Тесты `CatalogProjectionIndexTests` проверяют сохранность всех таблиц и откат частично созданных индексов при реальной DDL-ошибке. Не удаляйте старые индексы и не превращайте `instr` в токенизированный поиск без отдельной задачи.

Для `QueryGroupsAsync` вида «Папка» ограниченная оценка числа кандидатов выбирает существующий индекс пути только для небольшого диапазона. Оценка и результат читаются в одном снимке. Сохраняйте возврат к обычному плану для широких корней: безусловный range seek ухудшает чтение всего каталога. Это выбор плана чтения, без записи или удаления строк.

`_lastProjectionTiming` содержит диагностику последней актуальной проекции без путей/поискового текста. Performance runner сравнивает v0.10.8 `cb6d716` с текущей ревизией одним измерителем и дополнительно сверяет все столбцы media rows до/после. Разбивка этапов baseline недоступна; не выдавать её за сравнительный результат. См. [v0.10.9](docs/v0.10.9-search-sort.md) и точные отчёты CI соответствующего SHA.

## Продолжение после v0.10.6

`LibraryChangeCoordinator` ограничивает файловые события и сверку корней; `FileSystemObservationProbe` наблюдает оригиналы только для чтения. `LibraryCatalogSynchronizer` применяет наблюдения через SQLite CAS и публикует подтверждённые изменения, включая уже зафиксированное переименование после отмены. `MainWindow.Monitoring.cs` связывает мониторинг с UI и приостановкой перед переносами.

## Архитектура и инварианты

- Desktop получает сводку групп и ограниченные страницы из SQLite. `VirtualPhotoRows` держит кэш вокруг видимой области; viewer получает соседние элементы. Не возвращать глобальную коллекцию всех фотографий.
- `CatalogViewQuery` описывает фильтры/порядок. Фоновый обход использует keyset, случайные страницы — offset с индексами. Устаревшие UI-запросы отменяются.
- `BackgroundWorkScheduler` ограничивает очередь/конкуренцию и сохраняет ресурс для видимых превью. Бюджет декодированных изображений 256 MiB относится к кэшу, не всему RSS.
- SQLite: WAL, synchronous=FULL, короткие транзакции, stable asset ID, адресные обновления, backup перед миграцией, идемпотентные квитанции переноса.
- `FileMoveService`: подтверждённый план, связанные группы, SHA-256, durable-журнал, rename на одном томе / проверенная копия между томами, recovery и undo. Callback каталога может повторяться.
- Windows cleanup привязан к проверенному открытому handle. POSIX fallback сохраняет источник под журналируемым резервным именем; не заменять его обычным удалением по пути.
- Перед переносом ожидается завершение фактических читателей. Незавершённые операции блокируют новые переносы/карантин. Карантин повторно проверяет keeper; прямого удаления дублей нет.
- v0.10.3: единый реестр companions; копия на Windows сохраняет owner/group и DACL до первых байтов, неподдерживаемые политики блокируются. Журналы читаются потоково с лимитами; обратные операции сверяются с исходными по путям, хэшу, размеру и группе.
- Дубли хранятся в отдельной SQLite-сессии и показываются страницами. Keeper проверяется по всей сессии. Не возвращать список всех совпадений в RAM.
- Даты имеют отдельный статус ошибки и время повтора; ошибка чтения не стирает ранее известную дату. Schema 4 мигрируется с проверенным backup.
- ImageSharp удалён по решению пользователя. SkiaSharp и MetadataExtractor не требуют ключа; lock-файлы, NuGet audit и notices входят в сборку.
- Новые установки используют LocalAppData. Старый roaming-каталог и его журналы не разрывать. Карантин имеет явный выбранный путь и сохранённый реестр batch-папок для recovery/undo.
- Одновременные экземпляры защищены mutex и файловым lease каталога. Проверка UI использует собственный временный каталог.
- Иконки/PNG — WPF Resource. Не возвращать startup-зависимость от внешней Assets или Assembly.Location. `PreviewImage.Status` позволяет обычный binding вместо attached-property TypeConverter.

## Проверки

v0.10.4: `FolderInclusionRules` хранит включения и исключения, самое вложенное правило побеждает. Родительская галка имеет промежуточное состояние; просмотр папки не меняет правила. `IncludedFolders` добавлены в desktop_settings без сброса каталога.

HEIC/HEIF декодирует встроенный helper libheif 1.23.5/libde265 1.1.3. Один worker, timeout 15 s, Windows Job 1 GiB; parent держит исходник Read/FileShare.Read до фактического завершения. Не убирать Job, лимиты/lock и не добавлять fallback на WIC для HEIC. Это отдельный процесс, не OS sandbox. `tools/build-heif-codec.ps1` запускается Windows harness до .NET build. DLL, helper, LGPL sources/licenses должны попасть в `codecs/heif` рядом с EXE.

```bash
./tools/harness.sh
```

```powershell
./tools/harness.ps1
```

Windows harness собирает решение, выполняет тесты, публикует self-contained EXE, проверяет его встроенные ресурсы и запускает полноценное главное окно с отдельным временным каталогом. GitHub Actions запускает этот сценарий для push/PR в main. Результаты тестов и сборка доступны в артефактах соответствующего workflow.

Lock-профили разделены: обычные build/test используют `packages.lock.json`, публикация с `PhotoShelfPublish=true` — `packages.publish.lock.json` в каждом из четырёх `src`-проектов. Публикация остаётся в `RestoreLockedMode=true`; её RID и `PublishSingleFile` добавляют собственные зависимости SDK. SDK закреплён на 10.0.401 в `global.json` без roll-forward; CI читает этот файл. Обновляйте SDK и оба набора lock-файлов вместе, не отключайте locked mode в CI. `publish-dependencies.json` и `publish-dependency-audit.json` описывают граф опубликованного приложения.

Подтверждён [Windows CI 36347710370](https://github.com/BigGluk23/PhotoShelf/actions/runs/36347710370) на `0edf80035edb6d0776356f79331db240d1154e3a`: 255 тестов приложения, включая 39 Desktop-тестов, прошли без пропусков. Опубликованный EXE загрузил главное окно, синтетическое превью и нативный WebP-декодер, отвечал 6 секунд и штатно закрылся без ошибок. Скачанные TRX/smoke и аудит обоих графов зависимостей проверены. Подробности, ссылки на артефакты и границы измерений — в `docs/v0.10.3-review-fixes.md`; для последующих коммитов проверяйте их собственный CI. Предыдущая проверка v0.10.2 сохранена в `docs/v0.10.2-validation.md`.

v0.10.4: на `f879349` Windows harness подтвердил 298 passed / 0 failed / 0 skipped, включая 49 Desktop-тестов и HEIC 48 Мп. Опубликованный EXE открыл HEIC-превью, штатно закрылся без ошибок. Общий workflow 36397250675 помечен cancelled из-за запроса отмены, пересёкшегося с успешным завершением harness; не называйте его зелёным. Скачанные TRX/smoke и пакет проверены; точные ссылки, SHA256 и границы проверки — `docs/v0.10.4-folders-heif.md`. На Mac можно собрать WPF, но нельзя этим подтвердить Windows runtime. Native Windows-тесты на Mac явно пропускаются. Не считать пропуски успешными тестами и не выдавать зелёный внешний workflow без просмотра конкретных шагов/отчётов за доказательство.

Используйте синтетические файлы. Нельзя проверять перемещение на личной библиотеке. Обычный process-kill не моделирует отключение питания и физическую поломку диска.

## Оставшиеся ограничения
