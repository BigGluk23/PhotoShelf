# Передача PhotoShelf следующему агенту

## Начать здесь

Текущая поставка: **PhotoShelf Ultra v0.10.1**, строка версии сборки `0.10.1-ultra`, числовая версия `0.10.1.0`. Это Windows x64 C#/.NET 10/WPF приложение; основной сценарий — быстрый локальный менеджер фото и видео. Репозиторий уже существует, переписывать приложение с нуля не нужно.

Пользователь согласовал и получил реализацию этапов P0 «Быстрое и измеримое ядро» и «Безопасная организация файлов». Затем запросил сравнение улучшений, имя Ultra и единый архив для передачи. После сообщения об ошибке TypeConverterMarkupExtension при запуске выпущено исправление 0.10.1: WPF Resource вместо внешнего Content, pack URI, иконка трея из ресурса, полная диагностика и защита всего bootstrap. Файловый движок не менялся. См. docs/v0.10.1-startup-fix.md.

Распакуйте весь архив в отдельную папку. Исходники — `src/`, тесты — `tests/`, решение — `PhotoShelf.sln`. Запуск готового EXE: `releases/PhotoShelf-v0.10.1-ultra-win-x64/PhotoShelf.exe`, иконки и PNG встроены в EXE, внешняя папка `Assets/` не нужна.

## Реализованное состояние

- Desktop запрашивает сводку групп и страницы из `SqliteDesktopCatalogStore`. `VirtualPhotoRows` держит ограниченный кэш строк, viewer запрашивает соседние 11 элементов. Глобальной коллекции всех PhotoItem в MainWindow нет.
- `CatalogViewQuery` описывает фильтры и порядок. Фоновое последовательное чтение использует keyset; доступ к случайной странице — индексированный offset. База остаётся единственным рабочим каталогом Desktop.
- `BackgroundWorkScheduler` ограничивает очередь и конкуренцию, резервирует ресурс для интерактивных задач. Кэши ограничены; бюджет 256 MiB — не предел RSS процесса.
- SQLite: WAL, synchronous=FULL, короткие транзакции, stable asset ID, адресные обновления, счётчики размеров для дублей, резервная копия перед миграцией, квитанции идемпотентного переноса.
- `FileMoveService`: план, группы, проверяемый durable-журнал, SHA-256, rename на одном томе / verified copy между томами, повторяемый recovery, undo. Callback каталога может повториться и обязан быть устойчивым к повтору.
- В Windows удаление источника привязано к проверенному открытому handle. На POSIX исходник сохраняется под журналируемым резервным именем: это намеренно консервативный fallback переносимых тестов.
- Перед переносом завершаются фактические читатели; AsyncMediaImage позволяет приостановить только затронутые пути. Новые операции заблокированы при незавершённых журналах. Закрытие ожидает активную операцию и не допускает новую.
- Карантин перепроверяет keeper, использует неизменяемый снимок выбора, сохраняет данные каталога и допускает откат. Прямого удаления дублей нет.
- `App` удерживает mutex и файловый lease каталога от одновременных экземпляров.

## Проверки и то, что НЕ подтверждено

Сборка выполнена на macOS ARM64 с .NET SDK 10.0.401; WPF кросс-компилируется. В v0.10.0 прошли 107 обычных переносимых тестов (Domain 4, Application 75, SQLite 28); 3 scale-теста на 10k/100k/1M прошли отдельно при реализации v0.10.0. В v0.10.1 добавлены 3 переносимых теста полной диагностики исключений; текущие отчёты находятся в TestResults/startup-fix-portable. Исторический итог ядра v0.10.0 — 110 разных тестов. Шесть реальных process-kill сценариев включены в Application, это не шесть дополнительных тестов сверх 110.

Пять Windows native тестов явно пропущены на macOS. Шестнадцать WPF-тестов собраны, но не запускались (12 прежних + 4 новых проверки ресурсов запуска). Реального Windows UI, NTFS/ADS/EFS, FAT/exFAT/USB и отключения питания не проверяли. Успешная кросс-сборка не подтверждает эти сценарии. Для следующей технической работы приоритет — воспроизводимая Windows-проверка по чеклисту, а не заявление о полной безопасности или ускорении UI по SQL-замерам.

Обычный Windows-прогон:

```powershell
dotnet --info
dotnet build PhotoShelf.sln -c Release
./scripts/verify-windows.ps1
# Масштабные тесты отдельно, могут занимать несколько минут
./scripts/verify-windows.ps1 -Scale
```

Linux/macOS: запускать только Domain/Application/Infrastructure.Sqlite тесты. WPF не запускается на этих платформах. `global.json` выбирает установленный .NET 10 SDK с rollForward latestFeature. Обычная сборка требует восстановления NuGet; SDK, NuGet-кэш и IDE не включены. Готовый Windows EXE автономный и включает runtime.

```powershell
dotnet publish src/PhotoShelf.Desktop/PhotoShelf.Desktop.csproj -c Release -r win-x64 --self-contained true -p:PublishSingleFile=true -p:IncludeNativeLibrariesForSelfExtract=true -p:EnableCompressionInSingleFile=true -o artifacts/PhotoShelf-v0.10.1-ultra-win-x64
```

## Оставшиеся ограничения

- HEIC/HEIF/RAW встроенное декодирование и Live Photo resolver по content ID ещё не реализованы. Одноимённые фото+MOV без доказанной связи блокируются.
- Reparse/symlink и межтомовый перенос ADS/EFS блокируются. На одном томе rename сохраняет потоки/шифрование, это требует нативной проверки.
- Старые журналы v0.9.7 требуют ручного разбора. Не пытаться автоматически угадывать недостающие fingerprint/manifest.
- Видео использует WPF MediaElement и системные декодеры. Большие GIF/WebP могут показывать только первый кадр с пояснением.
- MainWindow всё ещё содержит часть оркестрации. Извлекать её постепенно по задаче; полный MVVM rewrite не был целью.
- Сопоставимого бенчмарка старого релиза и Ultra на Windows нет. 21×/24× относятся только к промежуточным и финальным индексам SQL новой реализации.

## Комплект и целостность

Единый архив содержит текущие исходники, тесты, документацию, скрипты, TRX, новую автономную Windows-сборку, старые поставки и резервные исходники. Исключены только восстановимые каталоги bin/obj, служебные .DS_Store и сам итоговый архив. Личные фото, рабочая база пользователя и секреты для продолжения разработки не нужны и не добавлялись.

Предыдущие полные ZIP не вложены повторно: это предотвращает рекурсивный рост, все самостоятельные релизы и исходные backups сохранены.

`PACKAGE-MANIFEST.json` перечисляет каждый включённый файл, размер и SHA-256. Проверьте после распаковки: `python scripts/verify-handoff.py .`. Рядом с ZIP лежит SHA-256 самого архива. Изменение любого исходника после распаковки ожидаемо нарушит исходный manifest; сохраните нетронутый архив как контрольную точку.

## Регрессия запуска 0.10.1

`Program.Main` перехватывает ошибку `App.InitializeComponent`; `App.OnStartup` защищает создание/показ LoadingWindow и MainWindow. Иконки — WPF Resource, не Content. Не возвращать зависимость startup UI от Assembly.Location или внешней Assets. ErrorReporter сохраняет полный exception.ToString() в `%APPDATA%\PhotoShelf\diagnostics\errors` (fallback TEMP).

`./scripts/test-startup-package.ps1 -ExePath ./releases/PhotoShelf-v0.10.1-ultra-win-x64/PhotoShelf.exe` проверяет опубликованный EXE отдельно от Assets и с пустой рабочей директорией. Нужна Windows. Флаг `--verify-startup-resources` создаёт App в verification-only режиме, который блокирует даже отложенный OnStartup; каталог и сканирование в этом режиме не запускаются. Проверка обычной несжатой test DLL не заменяет этот smoke-тест single-file EXE. На macOS он не выполнялся.
